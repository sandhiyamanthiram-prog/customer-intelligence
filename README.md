The Instamart Customer Intelligence is an end-to-end data analytics and AI-based support automation project developed using Python, Pandas, NumPy, Scikit-learn, SQLite and an offline mock LLM.

The project addresses three major business challenges:

1. Unreliable customer and order data containing duplicates, missing values, inconsistent spellings and invalid records.
2. Difficulty identifying valuable customers and predicting customers who are likely to stop ordering.
3. High volumes of customer support tickets requiring classification, privacy protection, policy-based answers and refund processing.

The project is divided into four connected parts:

| Part | Description | Technologies |
|---|---|---|
| Part A | Data cleaning, database creation and SQL analysis | Python, Pandas, SQLite |
| Part B | Customer segmentation and lapse prediction | Scikit-learn, K-Means, PCA, Logistic Regression, Random Forest |
| Part C | Support ticket classification and routing | Python, Regex, Mock LLM |
| Part D | Policy RAG assistant and refund automation agent | TF-IDF, Cosine Similarity, Mock LLM, SQLite |

All datasets are synthetic and generated using the supplied `generate_data.py` script.

All language-model interactions use the supplied offline `mock_llm.py`. No external API, API key or paid service is required.

### 3. TF-IDF Vectorisation and Retrieval

Scikit-learn's TfidfVectorizer was used to convert policy chunks into numerical vectors.

Cosine similarity was used to rank the chunks based on their similarity to the input question.

The retrieval function:

```python
retrieve(query, k=3)
```

returns the top three matching chunks with:

- source
- score
- text

For the query:

`refund policy late delivery`

the top three retrieved chunks belonged to:

`refund_policy.txt`

#### TF-IDF Explanation

Term Frequency (TF) measures how frequently a word appears in a document or chunk. Inverse Document Frequency (IDF) reduces the importance of words that appear frequently across many documents and gives more weight to distinctive terms.

One limitation of TF-IDF is that it relies heavily on word matching. Therefore, two sentences with the same meaning but different wording may receive a low similarity score.

### 4. Retrieval-Augmented Policy Assistant

The `answer(question)` function performs the following operations:

1. Receives a user question.
2. Retrieves the top three relevant policy chunks.
3. Constructs a context containing the source filename and retrieved text.
4. Sends the context and question to the offline mock LLM.
5. Returns the answer and the source documents.

The system prompt contains the words:

`POLICY ASSISTANT`

It instructs the model to answer only using the supplied policy context.

If the requested information is not available in the policy documents, the assistant returns:

```text
I could not find that information in the policy documents.
```

### 7. ReAct Agent Implementation

The refund agent follows the ReAct (Reasoning and Acting) approach.

The agent repeatedly:

1. Receives the user request.
2. Calls the mock LLM.
3. Identifies the requested tool.
4. Executes the corresponding Python function.
5. Appends the tool result to the conversation.
6. Continues until it receives a final response or reaches a safety limit.

The main function is:

```python
run_agent(
    user_message,
    scenario_id,
    max_iterations=6,
    token_limit=6000,
    time_limit_seconds=10
)
```

The agent returns:

- status
- final_answer
- steps
- llm_calls
- tokens_used

### 9. Safe Execution and Fallback Mechanisms

Three safety limits were implemented.

#### A. Maximum Iteration Limit

The agent stops after six model calls without receiving a final answer.

The status returned is:

`FALLBACK_MAX_ITERATIONS`

Scenario S7 was used to demonstrate this behaviour.

#### B. Token Limit

The agent tracks total token consumption after every model call.

If token usage exceeds the configured limit, it stops without executing the requested tool.

Demonstration:

```python
run_agent(
    user_message,
    scenario_id="S1",
    token_limit=200
)
```

Expected status:

`FALLBACK_TOKEN_LIMIT`

#### C. Time Limit

The agent uses `time.monotonic()` to calculate elapsed execution time.

If elapsed time reaches or exceeds the configured limit, the agent stops before making another model call.

Demonstration:

```python

    user_message,
    scenario_id="S1",
    time_limit_seconds=0
)
```

Expected status:

`FALLBACK_TIMEOUT`

### 11. ReAct Versus Plan-and-Execute

The ReAct agent performs actions through an iterative interaction between the model and the available tools.

For example, S1 required five model calls, while S5 required three and S6 required two.

A plan-and-execute approach could request the complete execution plan from the model in one call and then execute the steps in sequence. This could reduce model calls and token consumption for straightforward requests.

However, plan-and-execute may be less flexible when an unexpected observation occurs, such as an order not being found or an order having a cancelled status. It may need another planning call to adjust the execution plan.

For this refund workflow, ReAct is preferable because each tool result influences the next action. It provides better adaptability when checking order status, applying refund rules and deciding whether to issue, deny or escalate a refund. The additional model calls are justified by the need for reliable and policy-compliant refund decisions.

## Limitations and Next Steps

### Limitations

1. **Synthetic Dataset:** The project uses artificially generated data and does not represent real customer behaviour or actual Instamart operations.

2. **Lapse Prediction:** Model performance depends on the available six-month order history. More historical data and additional customer behaviour features could improve prediction quality.

3. **Customer Segmentation:** K-Means assumes clusters can be represented using distance-based relationships. Different clustering methods may produce different customer segments.

4. **Classification Accuracy:** The ticket classification system depends on the quality of the prompt and the capabilities of the supplied offline mock LLM.

5. **TF-IDF Retrieval:** TF-IDF primarily relies on keyword similarity and does not fully understand semantic meaning.

6. **Refund Automation:** The refund agent operates on simulated orders and a fictional refund policy. Real-world deployment would require authentication, transaction verification, audit logging and human approval workflows.

7. **Retention List Limitation:** The retention list is illustrative and not a leakage-free evaluation because the Premium segment flag is generated using the whole-window RFM data, including September activity. The lapse model itself uses only pre-cutoff order features.

8. **Offline Model:** The supplied mock LLM is deterministic and does not represent the full capabilities of a production language model.

### Next Steps

- Introduce more historical customer transaction data.
- Improve lapse prediction using additional behavioural features.
- Experiment with alternative clustering algorithms.
- Improve classification using more representative training examples.
- Explore semantic retrieval methods and embedding-based search.
- Add additional refund verification and approval controls.
- Integrate the system with a secure production database.
- Introduce monitoring dashboards for customer retention, ticket classification and refund processing.
- Evaluate the system using real-world operational metrics before production deployment.
